# StagePass + pgBackRest IA — Implementation Plan

**Date:** 2026-10-12 | **Host:** Arch Linux, 8 CPU, 7.5GB RAM | **Docker:** 29.8.1 / Compose 5.5.1
**Repo state at start:** empty directory, no README/docs/results, not a git repo.

## 1. Research question (used verbatim everywhere)

> How does pgBackRest with archived WAL improve PostgreSQL recoverability after accidental data loss compared with a consistent file-system snapshot alone, and what are the time and storage trade-offs of its backup strategies?

## 2. Pinned versions

- PostgreSQL `17` via `postgres:17-bookworm` (record exact minor, e.g. 17.6, at runtime).
- pgBackRest `2.59.x` (current stable 2.59.2 Sep 2026; PG17 support since 2.53.1) installed from PGDG APT in custom DB image; record `pgbackrest --version`.
- App: `python:3.12-slim`, FastAPI, Jinja2, psycopg2-binary, uvicorn.
- rsync `3.5.1`, pg_dump/pg_restore from PG17 client.

## 3. Architecture

- `db`: PG17 + pgBackRest + rsync in one container (simplest reliable; repo kept on separate volume so restore never overwrites its own recovery copy). `archive_command = pgbackrest --stanza=stagepass archive-push %p`, `restore_command` generated by pgBackRest restore (`archive-get`).
- `backup-tools`: Debian with pgbackrest+rsync+python, shares pgdata/repo/snapshot/results volumes; runs guarded rsync/pgBackRest ops.
- `app`: FastAPI server-rendered Jinja2, request-scoped DB connections with retry (survives restore downtime).
- Volumes: `pgdata`, `pgbackrest-repo`, `rsync-snapshots`, `results`.

## 4. App: StagePass

- `/`: StagePass brand, KJSCE Garba Eve hero (date field 2026-10-12, `12 OCT` label), venue/timing from seed, Register Now, ticket info, Maker Weekend + Open-Air Cinema cards. Palette: maroon/plum, saffron/coral, warm cream. Local CSS/SVG only.
- `/admin` (alias `/ops`): total bookings, attendees, per-event, Garba count prominent, recent regs, DB health; live SQL counts only.
- API: `GET /api/health`, `GET /api/events`, `GET /api/events/{slug}/registrations`, `GET /api/dashboard/summary`, `GET /api/registrations/recent`, `POST /api/events/{slug}/register` (transactional attendee+booking, validation, returns booking id).
- Schema: `events`, `attendees`, `bookings` with FKs/indexes; seed 100 bookings (20 Garba / 50 Maker / 30 Cinema), deterministic IDs + `simulation_batch_id`; rerunnable without duplicates.

## 5. Experiment sequence

### Scenario A — Consistent rsync snapshot without archived-WAL recovery
A1 reset→verify 100/20. A2 stop PG, `rsync -aHAX --delete` PGDATA→snapshot, manifest OUTSIDE PGDATA, restart. A3 20× HTTP Garba regs → 120/40. A4 incident DELETE Garba bookings → 0 Garba. A5 stop PG, guarded restore, restart, verify 100/20 + 20 IDs missing. NOT PITR.

### Scenario B — pgBackRest + WAL + PITR
B1 `check` ok. B2 `--type=full backup` + `info`. B3 same 20 HTTP regs → 120/40. B4 `pg_create_restore_point(stagepass_before_incident_<run>)` record LSN/time, `switch_wal()`, poll archiver + archive dir until WAL archived (fail-safe). B5 same incident. B6 `restore --type=name --target=<point> --target-action=promote`, start, confirm log `recovery reached target`. B7 verify 120/40 + 20 IDs present.

### Exp 2 — backup modes
Separate ~20k-row dataset (configurable down): full → mutate ~5% → diff → mutate → incr; 3 trials, medians; report pgBackRest `info` sizes with exact semantics (never conflate DB size vs compressed repo size).

### Exp 3 — pg_dump/pg_restore (supplementary)
`pg_dump -Fc` + `pg_restore` timing on same dataset if stable; else honest feature table (no WAL replay by itself).

## 6. Safety / controls

Every destructive op checks: lab marker (`STAGEPASS_LAB=1`, db `stagepass`), stanza/backup existence, path validation (reject empty, `/`, host PG dirs), prints plan, structured log, non-zero exit. No destructive app endpoint, no Docker socket in app. Per-scenario reset; ≥2 reproducibility runs; evidence preserved per run.
